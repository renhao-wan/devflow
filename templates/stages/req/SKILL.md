# 需求阶段（req）

## 何时使用

- 用户提出一个新功能、改造或问题，但验收标准还不清楚。
- 需求涉及多个子项目，需要先确认影响面。
- 跳过本阶段直接写代码会返工。

### 轻量模式（`--light`）

小功能（单文件或少量文件、无新依赖、无公共接口/数据变更）可合并 req 与 plan：

- 入口：`/devflow:req --light <需求>`，产出 `brief.md` 而不是 `req.md`。
- 必须写：目标、≥2 条可验证验收、本次不做、改动范围与测试计划、回滚。
- 可省略：方案候选对比、完整调研记录、技术约束全表；新增依赖不属于轻量范围。
- 硬触发（必须停止轻量并升级完整流程）：新增/升级依赖、公共接口/契约、数据结构/迁移、权限/认证/支付/并发/安全边界、不可逆操作、非测试/文档改动 >200 行、>10 文件或 >2 子项目。
- 软提示（先询问一次并记录，确认后可继续）：80–200 行或 5–10 个文件。

## 执行步骤

1. **复述目标**：用一句话写清“谁、在什么场景、要达成什么结果”。
2. **只问阻塞问题**：一次最多问 3 个会影响方案的问题；能靠读代码回答的，先读代码。
3. **划边界**：明确本次做、本次不做、以后再做的三张清单。
4. **写验收标准**：每条都必须可观察、可验证，避免“体验更好”这类描述。
5. **记录技术约束**：是否允许新增依赖、许可证政策、运行时/版本下限、离线或私有部署、数据驻留、必须兼容的接口；这些约束是 plan 阶段判断现成方案能否采用的前提。
6. **列影响面**：涉及哪些子项目、模块、接口、数据；是否需要迁移或兼容。
7. **标风险**：列出最大的 1–3 个不确定性，并说明先验证哪一个。依赖尚不确定的外部能力时，标记为“需在 plan 阶段调研”，不要在本阶段下结论。

## 门禁（全部满足才能进入 plan）

完整模式：

- [ ] 目标一句话，不含“优化”“完善”这类空词。
- [ ] 验收标准至少 2 条，每条能对应到具体操作或断言。
- [ ] 明确写出一件本次不做的事。
- [ ] 技术约束已记录（依赖政策、许可证、运行时、离线/部署要求）。
- [ ] 影响面列出具体子项目/模块，不写“全站”。
- [ ] 没有遗留的阻塞性问题。

轻量模式（`--light`）满足以下即可进入 implement：

- [ ] 目标一句话。
- [ ] 验收标准至少 2 条，且可观察、可验证。
- [ ] 明确写出一件本次不做的事。
- [ ] 改动范围与测试计划覆盖正常、边界、错误路径。
- [ ] 回滚方式一句话。
- [ ] 未命中硬触发；软提示已询问并在 `升级判断` 记录。

## 产出

- 默认写入 `docs/devflow/<slug>/req.md`，骨架见 `templates/req.template.md`。
- `--light` 写入 `docs/devflow/<slug>/brief.md`，骨架见 `templates/brief.template.md`；后续直接进入 implement，不再单独写 plan。
- `<slug>` 只用小写字母、数字和连字符（`[a-z0-9-]+`），不得包含 `/`、`\` 或 `..`。

完整模式结构：

```md
# <标题>

## 目标
## 场景与用户
## 验收标准
- [ ] ...
## 本次不做
## 技术约束
## 影响面
## 风险与待验证
```

## 边界

- 不在本阶段选技术方案，不写代码。
- 不把猜测写成结论；不确定的标记为“待确认”。
- 不代替 plan 阶段做现成方案调研；只记录约束，把“是否已有实现”留给 plan。
- 轻量模式一旦命中硬触发，先写 `## 升级判断` 并停止；不带着风险继续实现。
