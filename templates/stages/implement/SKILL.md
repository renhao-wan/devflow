# 实现阶段（implement）

## 何时使用

- 已有 `plan.md` 或轻量功能的 `brief.md`，任务拆分清楚。
- 需要真正改代码。

## 执行步骤

1. **一次一个任务**：按计划顺序推进，不顺手重构无关代码。
2. **测试先行**：能写测试的场景，先写一个会失败的测试，确认失败原因正确；步骤见 `devflow-tdd` 技能（已安装 superpowers 时也可用其 TDD 技法，门禁以本阶段为准）。
3. **最小实现**：让它变绿即可，再考虑清理；清理也必须让测试保持绿。
4. **小步提交**：每个任务完成即通过测试；需要提交时按仓库规范，不夹带无关改动。
5. **同步计划**：计划与实际偏离时，先更新 `plan.md`（轻量功能更新 `brief.md` 的「实施记录」），再继续。任务拆分表的「验收项」列标明该任务支撑的验收 ID，交付前运行 `node scripts/devflow-trace.mjs --root . --slug <slug>`（插件根可用时用 `devflow trace --slug <slug>`）核对验收缺口，确认没有验收项被遗漏。`devflow status` 会对照计划声明的文件与实际 git 改动，提示“计划外改动”和“计划未改动”；只提示，不阻断，但要逐条确认是更新计划还是补回遗漏项。
6. **记录证据**：运行过的测试命令与结果写进进度记录，不伪造。
7. **检查范围（轻量功能）**：非测试/文档改动超过 200 行、10 个文件或 2 个子项目，或涉及依赖、公共接口/契约、数据结构/迁移、权限/认证/支付/并发/安全边界、不可逆操作时，停止轻量流程并升级；80–200 行或 5–10 个文件先用 `AskUserQuestion` 询问一次，无法提问时回退为文本询问。完整任务不适用该升级规则，但范围明显扩大时仍要说明并更新 `plan.md`。计数口径：`git diff --numstat`（staged + unstaged），排除 `docs/devflow/**`、测试文件、lockfile 与生成物；多个子项目按改动文件数分别计。

## 可选完成条件（/goal）

本阶段可选使用原生 `/goal` 维持跨回合推进；插件不会自动设置，goal 也不替代门禁。建议条件：

- 计划中的任务全部完成，未完成项已写明原因；
- 每个改动模块有对应测试，且测试命令真实通过；
- `plan.md`（或轻量功能的 `brief.md` 实施记录）与实际改动一致。

需求未确认、计划待用户批准或需要人工决策时，不要启用 goal。

## 门禁（全部满足才能进入 test）

- [ ] 计划中的任务全部完成，或明确标注未完成项与原因。
- [ ] 每个改动的模块都有对应测试，或说明为什么无法测试。
- [ ] 本地构建/类型检查通过（若项目有）。
- [ ] 没有遗留调试代码、临时开关、被注释掉的旧实现。
- [ ] `plan.md`（或轻量功能的 `brief.md` 实施记录）与实际改动一致。

## 产出

- 代码改动。
- 更新 `docs/devflow/<slug>/plan.md` 的完成状态；轻量功能更新 `brief.md` 的「实施记录」；进度记录可使用 `templates/task-progress.template.md`。
- 新增/修改的测试文件。

## 技术栈规范

如果 `.claude/skills/devflow-<stage>/SKILL.md` 中存在「技术栈规范」映射，处理某个子项目时读取其对应文件；只读任务涉及的子项目，不预读全部。
技术栈规范与 `overrides` 冲突时以 `overrides` 为准，且不得放宽阶段门禁与安全底线。

## 边界

- 不擅自扩大范围；发现必须扩大时，停下来更新需求与计划；命中轻量硬触发时升级完整流程，不带着风险继续。
- 不为了让测试通过而削弱断言。
- 不提交密钥、内网地址、个人路径。
- 实验性改动失败时可用 `/rewind` 回到检查点，但它会丢弃当前会话改动，先确认范围；需要隔离并行工作时用 `/worktree`。
- 发现可复用的项目规则时，用 `devflow-rule-placement` 判断落位；不直接改 `.claude/skills/devflow-*` 投影。
