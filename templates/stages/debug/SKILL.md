# 排障阶段（debug）

## 何时使用

- 测试失败、运行报错、行为与预期不符。
- 问题原因不明，直接改代码属于猜测。

## 执行步骤

1. **复现**：拿到最小、稳定、可重复触发的命令或步骤。不能复现就不修。
2. **收集证据**：完整错误信息、日志、相关输入、最近改动（`git log`/`git diff`）。
3. **缩小范围**：用二分、注释、最小样例定位到具体文件与函数。
4. **提出假设**：一次只验证一个假设，写明“如果 X 成立，应观察到 Y”。
5. **最小实验**：用最快的方式验证，不修改生产逻辑。
6. **修根因**：修触发条件背后的原因，不吞异常、不加无意义重试。
7. **补回归测试**：先写一个在修复前会失败的测试，修复后确认它变绿。
8. **清除现场**：删除临时日志、调试代码、临时脚本。

## 门禁（修复才算完成）

- [ ] 有可重复的复现步骤或失败测试。
- [ ] 根因有证据支撑，不是“可能是”。
- [ ] 回归测试在修复前失败、修复后通过。
- [ ] 没有引入新的跳过或吞错。
- [ ] 调试残留已清理。

## 产出

- 修复代码与回归测试。
- 简短记录：现象、根因、修复方式、验证方式（写入 `docs/devflow/<slug>/debug.md` 或对话）。

## 边界

- 不在未复现时盲改。
- 不用“重试”“忽略异常”“加 sleep”掩盖问题。
- 不顺手重构无关代码；排障改动保持最小。
