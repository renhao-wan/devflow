# 审查阶段（review）

## 何时使用

- 测试通过，准备交付或提交。
- 改动涉及安全、数据、并发、对外接口。
- 需要独立视角检查自己刚写的代码。

## 执行步骤

1. **看全量 diff**：先看范围，确认没有意外文件、无关改动、生成物。
2. **按风险排序**：先查正确性与数据安全，再查边界与错误处理，最后查风格。
3. **逐项检查**：
   - 正确性：逻辑分支、空值、类型、时区、精度、并发。
   - 安全：注入、越权、敏感信息、日志泄露、依赖风险。
   - 兼容：接口变更、数据迁移、旧客户端。
   - 可维护：命名、职责、重复、死代码。
   - 测试：覆盖缺口与脆弱断言。
4. **给可执行结论**：每条问题写清文件:行号、问题、触发条件、建议。
5. **区分阻断与建议**：阻断项必须修复；建议项可记录。
6. **必要时用子代理**：调用 `devflow-code-reviewer` 获取独立意见，再做合并判断。

## 门禁（全部满足才能交付）

- [ ] diff 中没有与本任务无关的改动。
- [ ] 没有未处理的阻断级问题。
- [ ] 每条阻断项都有明确修复或明确的风险接受理由。
- [ ] 敏感信息扫描通过（密钥、内网地址、个人路径、调试输出）。
- [ ] 测试缺口已列出，或确认可接受。

## 产出

写入 `docs/devflow/<slug>/review.md`：

```md
# 审查记录

## 范围
## 阻断项
## 建议项
## 测试缺口
## 结论
```

## 边界

- 不把“看起来没问题”当结论；每条判断都要有依据。
- 不在审查阶段顺手大规模重构；发现问题交回实现阶段。
