# 代码审查

## 顺序（按风险，不按文件）

1. **范围**：有没有无关文件、生成物、调试代码、意外格式化。
2. **正确性**：分支、空值、类型、边界、并发、精度、时区。
3. **安全**：注入、越权、密钥与内网地址、日志泄露、反序列化、依赖风险。
4. **兼容**：接口变更、数据迁移、旧客户端、配置默认值。
5. **依赖与复用**：新增依赖是否有明确的采用/借鉴/自建依据；许可证是否与项目约束冲突；维护状态、已知漏洞与退出成本是否可接受；有没有重复实现已有能力。
6. **可维护**：命名、职责、重复、死代码、隐藏耦合。
7. **测试**：覆盖缺口、脆弱断言、被削弱的断言。

## 输出格式

每条问题：

```
[阻断|建议] 文件:行号
问题：一句话
触发条件：什么输入或状态会出问题
建议：具体改法
```

最后给结论：可以交付 / 修复阻断项后交付 / 需要重新设计。

## 判定标准

- **阻断**：会导致错误结果、数据损坏、安全漏洞、不可回滚的变更。
- **建议**：可维护性、性能、风格；不影响正确性。

## 常见漏检

- 只看了 diff，没看调用方。
- 测试通过就认为逻辑正确（断言可能写反）。
- 没检查错误路径：超时、空响应、部分失败。
- 没检查配置默认值在旧环境是否成立。
- 没检查日志里是否打印了敏感字段。
- 只信 `plan.md` 的复用结论，没有核对来源、许可证与维护状态。
- 引入新依赖只为省几行代码，忽略包体积、传递依赖与退出成本。

## 独立性

自己的代码自己审容易漏。需要第二视角时，用 `devflow-code-reviewer` 子代理，但子代理的结论必须自己核实后再采纳。

## 边界

- 不在审查阶段做大规模重构；发现问题交回实现阶段。
- 不把个人风格偏好当成阻断项。
